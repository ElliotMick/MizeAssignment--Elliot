     Key design decisions

     1. All shared state lives in SQL. With several instances, an in-memory
        limiter (such as the built-in ASP.NET RateLimiter) would let a supplier
        through N×100 times. The database therefore enforces both dedup and
        throttling, and one test proves this by running two API hosts against
        the same database.
     2. Dedup identity is the composite PK (SupplierId, ReservationId). A
        reservationId is unique per supplier. "Same details" means RoomId,
        CheckIn, CheckOut, Price and UpdatedAtUtc are all equal. In that case
        nothing is written and the outcome is Unchanged.
     3. Out-of-order updates. updatedAtUtc acts as the version.
        - If the incoming version is strictly older than the stored one, nothing
          is written. The outcome is Stale and the API answers 409 Conflict.
        - The 409 ProblemDetails includes the stored updatedAtUtc so the
          supplier can see why. IngestResult carries it as StoredUpdatedAtUtc.
        - An equal or newer version with different details is Updated. On a tie
          the last arrival wins, so changing only the price still updates.
     4. Concurrency uses the "read → decide (pure C#) → conditional write"
        pattern, retried up to 5 times.
        - Insert: the composite PK is the arbiter.
          ReservationRepository.TryInsertAsync catches SqlException 2627/2601
          (PK/unique violation) and returns false, meaning another instance
          inserted first. The service then re-reads and re-decides, which
          normally gives Unchanged. The constraint rejection is expected and
          handled, and it never reaches the client as an exception.
        - Update: optimistic concurrency with a ROWVERSION column (UPDATE …
          WHERE PK AND RowVersion = @Expected). If 0 rows change, the service
          re-reads and re-decides. This guarantees that an older version never
          overwrites a newer one, even under races.
        - Retries exhausted: the service throws
          System.Data.DBConcurrencyException, which the API returns as 503 +
          Retry-After: 1. The failure is transient, so a retry will succeed.
          This also keeps 409 meaning only "you sent an older version". The case
          is practically unreachable.
     5. The throttle is a sliding-window log in SQL, run as one batch in one
        round trip:
        - Take sp_getapplock on 'throttle:'+supplierId. This is a per-supplier
          mutex shared by every instance.
        - Delete log rows older than the window.
        - Count the rest.
        - If the count is below 100, insert a row (allowed). Otherwise increment
          ThrottledCount (rejected), using the same race-free counter upsert
          described in step 3 of the core flow.
        - Return the oldest timestamp in the window, which gives the Retry-After
          value.

        Only accepted requests occupy the window, so rejections don't extend the
        block. Requests that fail validation get a 400 before any database work
        and are not counted. The limit and window come from config
        (Throttling:PermitLimit=100, Throttling:WindowSeconds=60) and are
        validated on startup.
     6. The clock is an injected TimeProvider. Tests use FakeTimeProvider to
        step through the window deterministically.
     7. Stats are counters in SupplierStats. ingested is the number of requests
        that got past the throttle (created + updated + unchanged + stale). That
        includes stale ones answered with 409, which the breakdown lists
        separately. throttled is the number of 429s. The breakdown is included
        in the response. An unknown supplier gets 200 with all zeros.
     8. A resend must still match after a database round trip.
        - Columns are DATETIME2(7), and Dapper is mapped globally with
          SqlMapper.AddTypeMap(typeof(DateTime), DbType.DateTime2). Dapper's
          default is legacy datetime (3 ms precision), so without this map
          resends would never compare equal.
        - The request DTO uses DateTimeOffset, which is normalised to UTC.
        - Price is DECIMAL(18,2) and validation allows at most 2 decimals.
        - ID columns use COLLATE Latin1_General_100_BIN2. IDs are exact and
          case-sensitive, which also matches the binary resource compare used by
          sp_getapplock.
        - IDs are trimmed at the boundary.
     9. Migrations.
        - The schema is in a hand-written, re-runnable
          Migrations/001_InitialSchema.sql, embedded as a resource.
        - DatabaseMigrator creates the database if it is missing and applies
          scripts that dbo.SchemaMigrations doesn't list yet.
        - It holds an applock while applying them, so instances starting at the
          same time don't race.
        - It runs on startup when Database:ApplyMigrationsOnStartup=true (set in
          Development).
        - The script can also be run by hand: sqlcmd -S "(localdb)\MSSQLLocalDB"
          -d MizeReservations -i ….
        - The test fixture uses the same migrator.

     Body: {supplierId, reservationId, outcome:"Created", message}
     ────────────────────────────────────────
     Case: Exact resend
     Status: 200

     ────────────────────────────────────────
     Case: Changed details
     Status: 200
     Body: outcome:"Updated"
     ────────────────────────────────────────
     Case: Older version (incoming updatedAtUtc < stored)
     Status: 409 Conflict

     supplierId,
     reservationId, outcome:"Stale" and storedUpdatedAtUtc
     ────────────────────────────────────────
     Case: Over limit
     Status: 429 + Retry-After: <sec>
     Body: ProblemDetails
     ────────────────────────────────────────
     Case: Invalid/missing fields, checkOut ≤ checkIn, price < 0 or >2 dp

     DataAnnotations/IValidatableObject)
     ────────────────────────────────────────
     Case: Concurrency retries exhausted (practically unreachable)
     Status: 503 + Retry-After: 1
     Body: ProblemDetails
     ────────────────────────────────────────
     Case: Unexpected
     Status: 500
     Body: ProblemDetails (no stack trace), via .NET 8 IExceptionHandler

     Core flow (ReservationService.IngestAsync)

     1. now = timeProvider.GetUtcNow(), then
        repo.TryAcquireRequestSlotAsync(supplierId, now, limit, window). If the
        request is not allowed, return Throttled(RetryAfter).
     2. Run the loop (at most 5 attempts):
        - existing = repo.GetAsync(...).
        - No row: TryInsertAsync gives Created, or on a duplicate key continue.
        - existing.HasSameDetailsAs(incoming) gives Unchanged.
        - incoming.UpdatedAtUtc < existing.UpdatedAtUtc gives Stale.
        - Otherwise: TryUpdateAsync(incoming, existing.RowVersion) gives
          Updated, or on a row-version conflict continue.
     3. repo.RecordOutcomeAsync(supplierId, outcome, now). This uses UPDATE …
        WITH (UPDLOCK, SERIALIZABLE) then IF @@ROWCOUNT=0 INSERT inside a
        transaction, which is a race-free counter upsert.

● I made all five changes. The solution builds with no warnings, and all 61
  tests pass, both unit and integration on LocalDB.

  1. Insert first. StoreAsync now tries the INSERT before anything else, and a
     new reservation is stored in one round trip. If the composite key rejects
     it, the service reads the stored row and decides Unchanged, Stale or
     Update, keeping the row-version check on updates.
     - Cost: every resend (Unchanged or Stale) now pays for a rejected insert
       plus a read, where before it was just a read. That's the right trade if
       most traffic is new reservations; if suppliers mostly resend, it's
       slower. I noted this in the README.
     - Retest: removing the duplicate-key catch now breaks 6 integration tests,
       so they still depend on it.
  2. Configurable attempts. Ingest:MaxWriteAttempts is in appsettings.json
     (default 5, allowed 1–20) and is checked at startup. One unit test sets it
     to 3 and confirms the service gives up after 3 attempts.
  3. Business-rule check. At the start of IngestAsync, before the throttle or
     any database call, the service checks the rules the table enforces: ID
     length and non-blank, checkOut after checkIn, price ≥ 0, at most 2
     decimals, and the price limit. Every broken rule comes back in a single 400
     with outcome: "Invalid", keyed by field name, and an invalid request isn't
     counted against the supplier's limit.
     - One place for the rules: I moved them out of the request DTO, which now
       only checks that each field is present. Before, a rule broken via the API
       could never reach the service. The limits are constants on Reservation,
       next to the table they mirror.
     - Price can be 0: the table's constraint is Price >= 0, so 0 passes. Your
       example said price > 0; tell me if 0 should be rejected and I'll change
       both the check and the constraint.
  4. Queries. I moved them to one static class per table under
     Repository/Queries/ (ReservationQueries, SupplierRequestLogQueries,
     SupplierStatsQueries) rather than using regions. New queries for a table
     have an obvious home, and any future repository can reuse them; regions
     would only fold the text in one growing file. ReservationRepository now
     contains only the C# calls.
  5. Controller split. ReservationsController now has only its two endpoints.
     Turning a service result into an HTTP response (status codes, Retry-After,
     the error bodies) is in Controllers/IngestActionResults.cs.

  I also updated the README, and the existing Postman requests still pass.

● The gap is real, but neither check you're thinking of causes it.

  Where the checks don't cause it
  - The guard in RecordOutcomeAsync. It only rejects Throttled and Invalid, and
    neither outcome ever reaches that call. A throttled request returns at line
    39, and an invalid one at line 25. After StoreAsync, the outcome is always
    Created, Updated, Unchanged or Stale, so the guard never fires on a real
    request. It only protects against a coding mistake.
  - The rule check (FindRuleViolations). It runs before the slot is taken. An
    invalid request never occupies the window and never touches stats, so the
    two stay consistent.

  Where the gap actually is

  It's anything that ends the request between taking the slot (line 32) and
  recording the outcome (line 43). In that case the request uses one of the
  supplier's 100 slots, but SupplierStats never counts it.

  - StoreAsync throws. This happens when write attempts run out
    (DBConcurrencyException, a 503), or on a SQL error or timeout (a 500).
  - The client disconnects. We pass the request's CancellationToken everywhere.
    If the supplier hangs up after the INSERT commits but before the stats
    update, the reservation is stored but CreatedCount is never incremented.
  - RecordOutcomeAsync itself fails. It's a separate transaction, so it's not
    atomic with the reservation write.

  The result is that ingested + throttled can fall below the number of requests
  that passed the gate. A rejected request is counted atomically in the same
  transaction as the throttle decision. An allowed request only counts if
  everything after it succeeds.

  Proposed fix
  1. Count acceptance where we count rejection. The throttle batch would also
     increment a new AcceptedCount column when it allows a request, in the same
     transaction that records the slot. ingested would then always equal what
     the window saw, the same way throttled does today. RecordOutcomeAsync would
     only fill in the created / updated / unchanged / stale breakdown.
  2. Record failures. If StoreAsync throws, count a Failed outcome in the
     breakdown and rethrow, so ingested = created + updated + unchanged + stale
     + failed always adds up.
  3. Don't cancel the stats write. Pass CancellationToken.None to
     RecordOutcomeAsync. Once the reservation write has committed, a client
     disconnect shouldn't stop the counter from catching up.

  This needs a second migration (002_…sql) adding AcceptedCount and FailedCount,
  which the migrator already handles. Neither counter has any history yet, so
  existing rows start both at 0. I'd also add tests: a store failure gets
  counted as failed, and accepted equals the sum of the breakdown.

  What changed
  - Accepted requests are counted atomically. The throttle batch now updates
    SupplierStats for both decisions in the same transaction: AcceptedCount + 1
    when it allows a request, ThrottledCount + 1 when it rejects one. ingested
    in the stats response now reads AcceptedCount, so ingested + throttled
    always equals the requests the throttle saw.
  - Failures are counted. There's a new Failed outcome and FailedCount column.
    If storing throws, the service records Failed and then rethrows, so the
    supplier still gets the 503 or 500. The breakdown always adds up to
    ingested, and the stats response now includes "failed".
  - Recording the outcome can't be cancelled. It always runs with
    CancellationToken.None, so a supplier hanging up after the write no longer
    skips the counter.
  - One choice I made beyond what we discussed: if the stats write itself fails,
    the error is logged and the supplier still gets its success response,
    because the reservation is already safely stored. In that rare case the
    breakdown can be one short of ingested, but the reservation and the throttle
    stay correct.
  - Migration 002_AddAcceptedAndFailedCounts.sql adds both columns. It also
    backfills AcceptedCount for existing rows instead of starting them at 0, so
    existing suppliers don't suddenly show ingested: 0.

    - A store failure is counted as Failed and the error still reaches the
      caller.
    - Running out of write attempts is counted as Failed.
